# BUD-14

## Blob inventory filter

`draft` `optional`

A server can publish a cacheable Bloom filter of its blob inventory. Clients download the filter once and check many blob hashes locally, without disclosing which hashes they are checking.

A negative result means the hash was absent from the represented snapshot. A positive result means it might have been present. Neither result guarantees current availability; clients can fall back to [BUD-01](./01.md#head-sha256---has-blob) `HEAD /<sha256>` when they need a current answer.

## GET /inventory - Get inventory filter

Servers implementing this BUD MUST serve `GET /inventory` from the root of their domain. A successful response MUST contain the binary format defined below with `Content-Type: application/octet-stream`.

The endpoint MUST be publicly readable without authorization or payment and MUST return the same inventory representation regardless of the requesting client. Clients SHOULD omit credentials and identifying headers.

### Inventory scope

The inventory MUST include each distinct stored-byte SHA-256 hash that the server makes available for public retrieval at the snapshot cutoff. Retrieval may be served through the server's own storage, a CDN, or a configured storage backend. The inventory MUST NOT include blobs that are expired, banned, deleted, or restricted to particular users at that cutoff, even if their bytes remain on disk.

Servers MUST NOT include speculative availability from arbitrary upstream servers. Publicly available hashes known through configured redirects MAY be included, but the filter does not distinguish local storage from redirected retrieval.

Servers MUST capture a consistent inventory snapshot, or use an equivalent process that guarantees the same set. The cutoff describes that snapshot, not the time construction finished or the HTTP response was served. `snapshot_at` MUST be the Unix timestamp of the cutoff, rounded down to whole seconds. A timestamp comparison within the same second is therefore inconclusive.

All represented hashes MUST be inserted using the advertised parameters. A server MUST publish the completed header and bitmap atomically. Clients MUST NOT be served a partially built filter.

The inventory is advisory. Servers MUST enforce bans, expiration, and other retrieval policies independently of cached filters.

### Checking support

Servers implementing this BUD MUST respond to `OPTIONS /inventory` with `200 OK` or `204 No Content`, no body, and both `Allow` and `Access-Control-Allow-Methods` containing `GET` and `OPTIONS`. These headers MUST list any other methods supported at this endpoint. Support discovery MUST work even before the first snapshot is ready.

Clients MAY use this response to discover support. A failed inventory download MUST NOT be interpreted as an empty inventory.

### Caching and cross-origin requests

Servers MUST:

- Include a strong `ETag` on successful inventory responses, changing it whenever the representation changes, including its header.
- Support `If-None-Match` and return `304 Not Modified` when the client's cached representation matches the current one.
- Include `ETag` and `Cache-Control` on `304` responses.
- Send `Cache-Control: public, max-age=<seconds>, no-transform`, choosing a nonnegative lifetime appropriate to their publication cadence.
- Apply the cross-origin requirements of [BUD-01](./01.md#cross-origin-headers), including on `304` and error responses.
- Expose `ETag` and `Allow` through `Access-Control-Expose-Headers`.
- Allow the `If-None-Match` request header in CORS preflight responses so browser clients can revalidate explicitly.

The `snapshot_at` field MUST remain attached to its bitmap when cached or persisted. A `304` response, a new HTTP `Date`, or a cache's `Age` does not advance this cutoff. HTTP cache freshness and inventory freshness are different.

Servers SHOULD rebuild on a periodic cadence, coalescing additions and removals between publications. Servers MAY retain an unchanged snapshot and its ETag when the inventory has not changed. Servers SHOULD coordinate publication with large expiration sweeps and MAY publish earlier after substantial changes.

Example response (the body is binary, not shown):

```http
HTTP/1.1 200 OK
Content-Type: application/octet-stream
ETag: "inventory-1842"
Cache-Control: public, max-age=300, no-transform
Access-Control-Allow-Origin: *
Access-Control-Expose-Headers: ETag, Allow
```

### Status codes

| Status Code               | Meaning                                                          |
| ------------------------- | ---------------------------------------------------------------- |
| `200 OK`                  | A complete inventory snapshot is returned.                       |
| `304 Not Modified`         | The client's cached representation is still current.             |
| `429 Too Many Requests`    | The client has exceeded a rate limit.                            |
| `503 Service Unavailable` | No snapshot is ready, or the inventory service is unavailable.    |

An empty inventory MUST be represented by a valid `200` response containing an empty filter, not an error or a bodyless response.

## Binary format

Version 1 defines a Blossom-specific Bloom filter profile, including its input encoding, hash derivation, probe arithmetic, and bitmap layout. It is not a serialization of a particular library's filter object.

The representation consists of a 32-byte header followed immediately by the bitmap. All multibyte integers are unsigned and **little-endian**, regardless of the host CPU's byte order. Byte order for integers is separate from bit numbering within bitmap bytes.

| Offset | Bytes | Field          | Meaning                                              |
| ------ | ----- | -------------- | ---------------------------------------------------- |
| 0      | 4     | `magic`        | ASCII `BLMF` (`42 4c 4d 46`).                          |
| 4      | 1     | `version`      | `1`.                                                 |
| 5      | 1     | `algorithm`    | `1`, the double-hashing algorithm below.              |
| 6      | 1     | `k`            | Number of bit positions per hash, from 1 through 32.  |
| 7      | 1     | `reserved`     | Zero.                                                |
| 8      | 8     | `snapshot_at`  | Snapshot cutoff, Unix seconds.                       |
| 16     | 8     | `n`            | Number of distinct hashes inserted.                  |
| 24     | 8     | `m`            | Bitmap size in bits; a positive multiple of 8.       |
| 32     | `m/8` | `bitmap`       | Filter bits, initially all zero.                     |

The body MUST be exactly `32 + m/8` bytes long. Clients MUST reject unsupported versions or algorithms, nonzero reserved bytes, invalid parameters, and truncated or oversized representations. Rejection means the inventory is unavailable, not that a queried blob is absent.

Clients MUST impose a local maximum decoded response size and validate lengths before allocating memory based on the header. They MUST enforce that limit while reading the body, even when `Content-Length` is absent or incorrect. For HTTP content coding, these checks apply to the decoded representation. Exceeding a client's supported size means the inventory is unavailable, not empty.

Implementations MUST preserve integer precision when decoding the header and calculating bit positions; JavaScript implementations can use `BigInt`. Header values MUST NOT be rounded through floating-point conversions.

Version 1 supports only algorithm 1. Changing the input encoding, hash derivation, probe arithmetic, or bitmap layout requires a new profile identifier; implementations MUST NOT substitute a library's similarly named algorithm. Servers MUST continue to serve version 1 to requests that do not explicitly opt into a future format. Future format negotiation is outside this BUD.

### Hash-to-bit algorithm

The input `H` is the blob's 32-byte SHA-256 digest, decoded from hexadecimal if necessary. It is the hash of the stored bytes, including ciphertext when the blob is encrypted. Clients MUST NOT use a plaintext hash or encryption key in its place.

Algorithm 1 hashes the full identifier with a fixed domain prefix, then uses two words of the result for double hashing. The prefix is the ASCII string `blossom/inventory/v1` followed by exactly one zero byte; its hexadecimal encoding is `626c6f73736f6d2f696e76656e746f72792f763100`. Concatenation below is byte concatenation, not a textual encoding. The SHA-256 input is exactly 53 bytes.

```text
D = SHA256(ASCII("blossom/inventory/v1") || 0x00 || H)
h1 = unsigned little-endian integer from D[0:8]
h2 = unsigned little-endian integer from D[8:16], bitwise OR with 1

for i = 0 through k - 1:
    position = (h1 + i * h2) mod m
    byte_index = floor(position / 8)
    bit_mask = 1 << (position mod 8)
```

Arithmetic in `h1 + i * h2` MUST be performed without integer overflow; in particular, it MUST NOT wrap at 64 bits before reduction modulo `m`. The slices use zero-based, end-exclusive byte indexes. Bits within each bitmap byte are numbered from least significant to most significant.

An equivalent implementation avoids a wide multiplication for every probe:

```text
position = h1 mod m
step = h2 mod m
repeat k times:
    use position
    position = (position + step) mod m
```

The addition MUST still be exact. After exact reduction of the 64-bit words, JavaScript may use integer-valued `Number` arithmetic for this loop when `m <= 2^52`. For arbitrary permitted sizes, implementations need overflow-safe modular addition or wider integers.

Making the stride odd avoids a zero stride and gives a full cycle for power-of-two bitmap sizes. It does not guarantee a full cycle for every permitted `m`; repeated positions are allowed and MUST NOT be skipped or replaced. The error-rate formulas below are estimates for well-distributed inputs, not guarantees for every parameter combination.

To insert a hash, set each selected bit with bitwise OR. To test a hash, check those same positions:

- If any selected bit is zero, return **absent from the snapshot**.
- Otherwise, return **possibly present in the snapshot**.

For an empty inventory, servers MUST use `n = 0`, `m = 8`, `k = 1`, and a single zero bitmap byte.

### Sizing and rebuilding

For a nonempty inventory of `n` hashes and target false-positive probability `p`, conventional sizing estimates are:

```text
m = max(256, 8 * ceil((-n * ln(p) / (ln(2) * ln(2))) / 8))
k = max(1, min(32, floor((m / n) * ln(2) + 0.5)))
```

Servers SHOULD target a false-positive probability of 1% or lower. These are approximate sizing formulas, not a guarantee for individual queries or adversarial inputs. The 256-bit minimum in this sizing recommendation avoids extremely small filters where the approximation can be particularly inaccurate; it is not a wire-format minimum. Implementers SHOULD check measured error rates for their chosen sizing policy, especially for small inventories or unusually low targets. The header's actual `m` and `k` are authoritative; clients MUST NOT recalculate them from `n`.

At a 1% target, the bitmap uses approximately 1.2 bytes per inserted hash: about 12 KB for 10,000 hashes, 1.2 MB for one million, or 12 MB for ten million. Servers MAY allocate additional capacity for growth.

A standard Bloom filter cannot safely remove an entry by clearing its bits, since other entries may share them. Servers MUST NOT clear individual bits to implement deletions. Servers SHOULD rebuild each published snapshot from the live inventory, resizing as appropriate. Rebuilding requires only the stored hashes, not reading or hashing blob contents.

Servers MAY monitor bitmap occupancy using `fill = set_bits / m` and the rough error estimate `fill^k` to detect saturation and choose a larger bitmap on rebuild. This estimate is diagnostic, not proof of accuracy or truthful inventory contents.

This BUD specifies one full-inventory filter. It does not require prefix buckets, incremental updates, or a particular database index.

## Client behavior and freshness

Clients SHOULD reuse a cached filter for multiple local checks and refresh it on demand rather than polling continuously. An ETag saves bandwidth when the representation is unchanged; it does not make downloading a changed filter cheaper.

Clients MUST distinguish snapshot results from current existence:

| Result   | Interpretation and possible action                                                                 |
| -------- | -------------------------------------------------------------------------------------------------- |
| Negative | The hash was absent at the cutoff. It may have been uploaded or restored since then.                |
| Positive | The hash may have been present at the cutoff. It may be a false positive or have since been removed. |

If a client knows a blob was uploaded to this server after the cutoff, it SHOULD refresh the filter or fall back to `HEAD /<sha256>` rather than treating a negative result as a missing replica. Upload timing is specific to the server: a file's modification time or the time it was uploaded elsewhere is not sufficient.

Clients MUST account for clock uncertainty when comparing upload times with `snapshot_at`. Same-second timestamps, unknown upload times, and uncertain clock offsets cannot establish that an upload is represented.

Clients requiring current confirmation SHOULD use `HEAD /<sha256>`, or `GET /<sha256>` if they need the bytes anyway. A positive filter result MUST NOT be treated as proof of complete storage, integrity, or retention. Neither a filter nor a successful HEAD guarantees future availability.

Failures such as timeouts, authorization errors, rate limits, unsupported formats, and unavailable inventories MUST NOT be interpreted as absence. A negative snapshot result alone SHOULD NOT trigger destructive actions or unnecessary replica replacement.

## Privacy

Downloading the same full filter lets clients check hashes locally without revealing their targets or which hashes belong together. The server can still observe the client's network identity, request timing, and refresh frequency. A subsequent HEAD, GET, or upload reveals the hash involved in that operation.

The public filter allows anyone to test candidate hashes offline. It exposes the approximate size of the inventory, and successive snapshots can reveal membership changes for known hashes. Servers SHOULD NOT publish per-user or per-drive inventories through this endpoint.

The fixed domain-separated rehash mixes all identifier bytes into the probe material; it does not conceal membership from anyone who knows or can derive a candidate blob hash. Algorithm 1 has no secret key or rotating seed. Rechecking a candidate against the same filter yields the same result, not an independent test that reduces false-positive uncertainty.

Randomized encryption makes ciphertext hashes difficult to predict from plaintext. Deterministic or content-derived encryption does not: an observer who can derive a candidate blob hash can test it against the filter. This BUD does not hide that membership information or replace encryption.

Previously downloaded snapshots cannot be recalled when a blob is banned or deleted. A server can also publish an inaccurate filter; transport authentication does not prove that it stores the advertised blobs.

## Test vectors

These vectors exercise the binary encoding and membership algorithm. Their small filters are not recommended production sizing.

### Two hashes

Parameters: `snapshot_at = 1700000000`, `n = 2`, `m = 64`, `k = 3`.

| Blob SHA-256                                                     | Bit positions |
| ---------------------------------------------------------------- | ------------- |
| `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` | 3, 18, 33     |
| `2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824` | 47, 30, 13    |

The domain-separated digests `D`, in the same order, are:

```text
83aaab4507d911434eddee20cbd2d95c239909f0d597f250f51b0bcb9f04938d
ef3fcb7925e80b1f6e492908360f7190baffbc369e4be070c49305c45128da4e
```

Their `(h1, h2)` integer values in hexadecimal are respectively `(4311d90745abaa83, 5cd9d2cb20eedd4f)` and `(1f0be82579cb3fef, 90710f360829496f)`. Both second words are even before the required OR with 1.

Header, hexadecimal:

```text
424c4d460101030000f153650000000002000000000000004000000000000000
```

Bitmap, hexadecimal:

```text
0820044002800000
```

Complete 40-byte body, hexadecimal:

```text
424c4d460101030000f1536500000000020000000000000040000000000000000820044002800000
```

Both inserted hashes test positive. The hash `486ea46224d1bb4fb680f34f7c9ad96a8f24ec88be73ea8e5a6c65260e9cb8a7` selects positions `21, 58, 31` and tests negative.

### Non-power-of-two bitmap

Using the same two hashes with `m = 72` and `k = 3`, their positions are respectively `3, 50, 25` and `7, 14, 21`. The nine-byte bitmap is:

```text
884020020000040000
```

This vector detects implementations that incorrectly wrap arithmetic at 64 bits before reducing modulo `m`: the second hash's third position would incorrectly be `5` instead of `21`.

### Empty inventory

Parameters: `snapshot_at = 1700000000`, `n = 0`, `m = 8`, `k = 1`.

Complete 33-byte body, hexadecimal:

```text
424c4d460101010000f15365000000000000000000000000080000000000000000
```

Every hash tests negative.
