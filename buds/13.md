# BUD-13

## Path-based blob upload

`draft` `optional`

_All pubkeys MUST be in hex format_

This document supersedes the `PUT /upload` endpoint definition from [BUD-02](./02.md).

Servers that implement this document MAY continue to support the `PUT /upload` endpoint from [BUD-02](./02.md) for compatibility.

Defines the `PUT /<sha256>` and `POST /<sha256>` endpoints, and the optional `QUERY /<sha256>` upload acceptance check.

The [Blob Descriptor](./02.md#blob-descriptor) type is defined in [BUD-02](./02.md).

The `<sha256>` path segment MUST be a lowercase hex-encoded sha256 hash of the blob being stored.

## PUT /sha256 - Upload Blob

The `PUT /<sha256>` endpoint MUST accept binary data in the request body.

The server MUST NOT modify the blob in any way and MUST compute the sha256 hash over the exact bytes received. This requirement ensures that users can re-upload blobs to other servers without discrepancies.

Clients SHOULD include `Content-Type` and `Content-Length` headers specifying the MIME type and size of the blob.

If the computed sha256 of the request body does not match the `<sha256>` path segment, the server MUST reject the request with `409 Conflict` and MUST NOT persist the blob.

Servers MUST reject `PUT /<sha256>` requests containing one or more `url` query parameters with `400 Bad Request`. Remote source references are only accepted in the request body of `POST /<sha256>`.

If the blob was newly stored, the endpoint MUST respond with `201 Created` and a [Blob Descriptor](./02.md#blob-descriptor) in the response body.
If the blob already exists, the endpoint MUST respond with `200 OK` and a [Blob Descriptor](./02.md#blob-descriptor) in the response body.

Servers MUST handle uploads correctly regardless of whether the client performed a pre-flight check such as [`QUERY /<sha256>`](#query-sha256---check-upload-acceptance-optional) or `HEAD /upload` first.

### Checking support

Clients SHOULD send `OPTIONS /<sha256>` using any syntactically valid hash as defined in [BUD-01](./01.md#feature-discovery). Path-based uploads are supported when both `Allow` and `Access-Control-Allow-Methods` include `PUT`; the presence or absence of `POST` independently indicates mirroring support.

### Status codes

Servers SHOULD use the following status codes for `PUT /<sha256>` responses:

| Status Code                  | Meaning                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `200 OK`                     | The blob already exists and the server is returning the existing [Blob Descriptor](./02.md#blob-descriptor). |
| `201 Created`                | The blob was stored successfully and the server is returning its [Blob Descriptor](./02.md#blob-descriptor). |
| `400 Bad Request`            | The sha256 path, request headers, body, or query parameters are malformed.                                   |
| `401 Unauthorized`           | Authorization is required and missing or invalid. See [BUD-11](./11.md#endpoint-authorization-requirements). |
| `402 Payment Required`       | Payment is required before the upload can proceed. See [BUD-07](./07.md).                                    |
| `403 Forbidden`              | The request is understood but not allowed by server policy.                                                  |
| `409 Conflict`               | The sha256 from the path does not match the request body.                                                     |
| `411 Length Required`        | A required `Content-Length` header is missing.                                                               |
| `413 Content Too Large`      | The blob exceeds server size limits.                                                                         |
| `415 Unsupported Media Type` | The blob type is not supported.                                                                              |
| `429 Too Many Requests`      | The client has exceeded a rate limit or quota.                                                               |
| `503 Service Unavailable`    | The upload service is temporarily unavailable.                                                               |

If included, `X-Reason` MUST be treated as a human readable diagnostic message only and clients MUST NOT parse it for control flow.

## POST /sha256 - Mirror Blob

Servers MAY accept `POST /<sha256>` requests containing one or more source references that tell the server where to fetch the blob. This replaces the mirroring flow from [BUD-04](./04.md) while retaining the blob hash in the path and allowing clients to reuse the same [BUD-11](./11.md) `upload` authorization token as long as at least one `x` tag matches the `<sha256>` path.

The request body MUST be UTF-8 plain text containing one source reference per line. Clients SHOULD set the `Content-Type` header to `text/plain; charset=utf-8`. Servers MUST accept lines separated by either LF or CRLF, MUST accept a final line without a trailing newline, and MUST ignore empty lines. Leading and trailing ASCII whitespace is not part of a source reference and MUST be removed from each line.

The request `Content-Type` and `Content-Length` headers describe the source list itself and MUST NOT be used as metadata for the mirrored blob.

Each non-empty line MUST be one of the following:

- An absolute `http` or `https` URL.
- A valid [`blossom:` URI from BUD-10](./10.md).

The request body MUST contain at least one valid source reference after empty lines are removed. Servers MUST reject an empty body, invalid UTF-8, or any malformed or unsupported source reference with `400 Bad Request`.

To provide a single HTTP source, clients MUST send one line:

```http
POST /b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553
Content-Type: text/plain; charset=utf-8

https://cdn.example.com/b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553.pdf
```

Clients MAY mix HTTP URLs and Blossom URIs in the same request body:

```http
POST /b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553
Content-Type: text/plain; charset=utf-8

https://cdn-a.example.com/b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553.pdf
https://cdn-b.example.com/b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553.pdf
blossom:b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553.pdf?xs=cdn-c.example.com&as=ec4425ff5e9446080d2f70440188e3ca5d6da8713db7bdeef73d0ed54d9093f0
```

For a `blossom:` URI, the sha256 hash in the URI MUST match the `<sha256>` path segment. Servers MUST reject the request with `409 Conflict` if any `blossom:` URI contains a different hash. Servers MUST resolve valid `blossom:` URIs using the [BUD-10 resolution strategy](./10.md#resolution-strategy).

When multiple source references are provided, servers MAY try any or all of them in any order. Servers MUST only store the blob if the sha256 hash of the fetched bytes matches the `<sha256>` path segment. If the fetched blob hash does not match the `<sha256>` path segment, the server MUST reject the request with `409 Conflict` and MUST NOT persist the blob.

The destination server SHOULD use the `Content-Type` header returned from the successful origin response to infer the MIME type of the blob. If the `Content-Type` header is not present, the destination server SHOULD attempt to detect the `Content-Type` from the blob contents and file extension, falling back to `application/octet-stream` if it cannot determine the type.

Servers MAY use the origin `Content-Length` header to reject blobs that exceed server size limits before downloading the full response.

If the blob was newly stored, the endpoint MUST respond with `201 Created` and a [Blob Descriptor](./02.md#blob-descriptor) in the response body.
If the blob already exists, the endpoint MUST respond with `200 OK` and a [Blob Descriptor](./02.md#blob-descriptor) in the response body.

### Checking support

Clients SHOULD send `OPTIONS /<sha256>` using any syntactically valid hash as defined in [BUD-01](./01.md#feature-discovery). Mirroring is supported when both `Allow` and `Access-Control-Allow-Methods` include `POST`; a server MAY advertise `PUT` while omitting `POST` when it supports direct uploads only.

### Status codes

Servers SHOULD use the following status codes for `POST /<sha256>` responses:

| Status Code                  | Meaning                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `200 OK`                     | The blob already exists and the server is returning the existing [Blob Descriptor](./02.md#blob-descriptor). |
| `201 Created`                | The blob was mirrored and stored successfully and the server is returning its [Blob Descriptor](./02.md#blob-descriptor). |
| `400 Bad Request`            | The sha256 path or request body is malformed, empty, or contains an unsupported source reference.            |
| `401 Unauthorized`           | Authorization is required and missing or invalid. See [BUD-11](./11.md#endpoint-authorization-requirements). |
| `402 Payment Required`       | Payment is required before mirroring can proceed. See [BUD-07](./07.md).                                    |
| `403 Forbidden`              | The request is understood but not allowed by server policy.                                                  |
| `405 Method Not Allowed`     | The server does not support mirroring and returns an `Allow` header listing its supported methods.           |
| `409 Conflict`               | The sha256 from the path does not match a `blossom:` URI or the fetched remote blob.                         |
| `413 Content Too Large`      | The mirrored blob exceeds server size limits.                                                                |
| `415 Unsupported Media Type` | The mirrored blob type is not supported.                                                                     |
| `429 Too Many Requests`      | The client has exceeded a rate limit or quota.                                                               |
| `502 Bad Gateway`            | The server could not resolve or fetch the blob from any source reference, or every origin response was unusable. |

If included, `X-Reason` MUST be treated as a human readable diagnostic message only and clients MUST NOT parse it for control flow.

## File extension normalization (Optional)

When storing blobs, servers MAY normalise the file extension to a standard format (e.g. `.pdf`, `.png`, etc.) based on the MIME type of the blob. This can be especially useful when the `GET /<sha256>` endpoint is redirected to an external URL (see the [proxying and redirection section from BUD-01](./01.md#proxying-and-redirection-optional)), as external servers may rely on the file extension to serve the blob correctly.

## Reverse proxies and path-based access rules

`PUT /<sha256>` and `POST /<sha256>` share a path with the read endpoints `GET /<sha256>` and `HEAD /<sha256>` from [BUD-01](./01.md). Reverse proxies, load balancers, CDNs, and web application firewalls often apply policy by path alone, for example a public or cached rule matching `/<sha256>` and a separate authenticated or rate limited rule matching `/upload`. With such a configuration, writes to `/<sha256>` silently inherit the read policy. No error is produced, so the misconfiguration can go unnoticed.

Operators that enable this endpoint behind an intermediary SHOULD review any rules that match `/<sha256>` and SHOULD distinguish requests by method as well as by path. In particular:

- Authentication, payment ([BUD-07](./07.md)), rate limiting, and access control applied to `/upload` SHOULD also be applied to `PUT`, `POST` and `QUERY` requests on `/<sha256>`, and read-only policy MUST NOT be extended to them. `QUERY` is a safe method, but it answers on behalf of an upload and may return a [BUD-07](./07.md) payment request for one. For example, a paid read window that allows repeated `GET` requests must not also allow repeated uploads.
- Request body size limits, timeouts, and request buffering configured for `/upload` SHOULD also be applied to `PUT /<sha256>`. Rules written for reads often have small body limits or none at all.
- Caches MUST NOT store responses to `PUT` or `POST` requests, and SHOULD invalidate any cached negative response (such as `404 Not Found`) for `/<sha256>` after a successful upload.
- Intermediaries that answer `OPTIONS` requests themselves SHOULD advertise `PUT`, `POST` and `QUERY` in `Allow` and `Access-Control-Allow-Methods` only when they forward those methods to the server. See [Checking support](#checking-support).

Operators that cannot apply method-based rules SHOULD NOT advertise `PUT`, `POST` or `QUERY` on `/<sha256>`, and SHOULD continue to serve uploads through `PUT /upload` from [BUD-02](./02.md).

## QUERY /sha256 - Check upload acceptance (Optional)

Servers MAY implement `QUERY /<sha256>` so clients can check whether a `PUT /<sha256>` upload would be accepted before sending the blob. `QUERY` is the safe, idempotent HTTP method with a request body defined in [RFC 10008](https://www.rfc-editor.org/rfc/rfc10008). Using it avoids the misuse of `HEAD` in [`HEAD /upload` from BUD-06](./06.md#head-upload---upload-requirements-optional), whose request headers describe a different request rather than the target resource.

This pre-flight request is only an optimization. Clients MAY skip it entirely, and the result is not a guarantee of the eventual `PUT /<sha256>` outcome because server state may change between requests. Servers MUST handle `PUT /<sha256>` correctly whether or not the client sent `QUERY /<sha256>` first.

Clients that want to check whether a blob already exists on the server SHOULD use [`HEAD /<sha256>` from BUD-01](./01.md#head-sha256---has-blob).

### Request

The `<sha256>` path segment identifies the blob that will be uploaded. The request body MUST be a JSON object describing the blob, and clients MUST set the `Content-Type` header to `application/json`.

- `size` (required): An integer representing the blob size in bytes.
- `type` (optional): A string specifying the blob's MIME type, like `application/pdf` or `image/png`.

Clients SHOULD NOT include any other fields. Servers MUST ignore every field other than `size` and `type`, and MUST NOT let other fields affect the response.

A `QUERY /<sha256>` request with this body asks whether a `PUT /<sha256>` request with `Content-Length` set to `size`, `Content-Type` set to `type`, and the same `Authorization` header would be accepted.

Clients SHOULD include the same `Authorization` header they intend to send with the `PUT /<sha256>` request. A single [BUD-11](./11.md#endpoint-authorization-requirements) `upload` token with an `x` tag matching `<sha256>` is valid for both requests.

```http
QUERY /b1674191a88ec5cdd733e4240a81803105dc412d6c6708d53ab94fc248f4f553
Content-Type: application/json
Authorization: Nostr eyJraW5kIjoyNDI0MiwiY29udGVudCI6IlVwbG9hZCBibG9iIiwi...

{"size": 184292, "type": "application/pdf"}
```

### Response

The server MUST evaluate the request against the same policies it would apply to `PUT /<sha256>` with the same `Authorization` header, `Content-Length` and `Content-Type`. The response body MAY be empty. If the server includes a body, clients MUST NOT depend on its contents.

`QUERY /<sha256>` MUST NOT store the blob or otherwise change the blob's state on the server. Servers MAY create transient records needed to answer the request, such as a payment request issued with a `402 Payment Required` response.

Responses to `QUERY` are cacheable by default, but an acceptance result depends on the requesting user and on current server state. Servers MUST include `Cache-Control: no-store` in every `QUERY /<sha256>` response.

Servers SHOULD include `Access-Control-Expose-Headers` listing `X-Reason` and any [BUD-07](./07.md) `X-{payment_method}` headers so browser clients can read them.

Servers SHOULD respond with the status code that `PUT /<sha256>` would return for the described request, as listed in [PUT /sha256 status codes](#status-codes), with the following differences:

- `200 OK` means the upload would be accepted and the client MAY proceed with `PUT /<sha256>`. Servers MUST NOT respond with `201 Created`.
- `400 Bad Request` also covers a request body that is not valid JSON, is not `application/json`, or lacks `size`.
- `409 Conflict` and `411 Length Required` do not apply, because no blob or blob `Content-Length` is sent.
- `413 Content Too Large` and `415 Unsupported Media Type` describe the blob given by `size` and `type`, not the `QUERY` request body.

If included, `X-Reason` MUST be treated as a human readable diagnostic message only and clients MUST NOT parse it for control flow.

After receiving `200 OK`, clients MUST still be prepared for `PUT /<sha256>` to return any status code defined for that endpoint, including `200 OK` if the blob was stored by another request in the meantime.

### Payment

When `QUERY /<sha256>` returns `402 Payment Required`, clients MUST NOT retry the `QUERY` request with payment proof. Clients SHOULD complete the payment and send the proof with the `PUT /<sha256>` request, as described in [BUD-07](./07.md).

### Checking support

Clients SHOULD send `OPTIONS /<sha256>` using any syntactically valid hash as defined in [BUD-01](./01.md#feature-discovery). The acceptance check is supported when both `Allow` and `Access-Control-Allow-Methods` include `QUERY`. Servers that support it SHOULD also include `Accept-Query: application/json` in the `OPTIONS` response.

Reverse proxies, CDNs, firewalls and HTTP frameworks may reject `QUERY` even when the origin server supports it, for example by responding with `405 Method Not Allowed` or `501 Not Implemented`, or by failing the request before it reaches the server. Clients MUST treat any such failure as the check being unavailable and continue with `PUT /<sha256>` or a legacy [`HEAD /upload`](./06.md#head-upload---upload-requirements-optional) check. Operators SHOULD NOT advertise `QUERY` unless every intermediary in front of the server forwards it.

Browser clients MUST send the method name in uppercase (`QUERY`), since the Fetch standard does not normalize the case of methods it does not recognize.

### Legacy `HEAD /upload`

[`HEAD /upload` from BUD-06](./06.md#head-upload---upload-requirements-optional) is unrecommended. New servers SHOULD implement `QUERY /<sha256>` instead of `HEAD /upload`. Servers MAY keep `HEAD /upload` for existing clients. Clients SHOULD prefer `QUERY /<sha256>` when it is advertised, and MAY fall back to `HEAD /upload` when it is not.

## HTTP 100 Continue (Optional)

Clients MAY use the HTTP `Expect: 100-continue` mechanism with `PUT /<sha256>` to allow a server or intermediary to reject an upload before the request body is sent.

Servers MAY support this optimization, but clients MUST NOT rely on it. Browsers cannot send the `Expect` header, and many reverse proxies answer `100 Continue` themselves without consulting the server.

Clients that need an explicit pre-flight mechanism SHOULD use `QUERY /<sha256>` when it is supported.
