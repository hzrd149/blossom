# BUD-16

## Directory manifests

`draft` `optional`

This document defines a deterministic MessagePack format for grouping Blossom blobs into named directory trees.

Clients upload directory manifests as normal Blossom blobs. Servers do not need to implement this BUD.

## Encoding Choice

Directory manifests use MessagePack because it is compact, supports byte arrays directly, and has mature Rust and TypeScript libraries.

Local benchmarks supported MessagePack as a fast practical choice for this manifest shape, though exact results varied by implementation.

This BUD fixes the MessagePack field order, sort order, integer encoding, and test vectors so manifest hashes are reproducible across implementations.

FlatBuffers can be competitive for reads, but was not chosen because it requires schema tooling or generated bindings and produced larger payloads in local manifest benchmarks.

## Media Type

Directory manifests SHOULD use the following media type when a media type is known:

```text
application/vnd.blossom.directory+msgpack
```

Clients SHOULD use the `.bdir` file extension in [BUD-10](./10.md) `blossom:` URIs.

## Manifest Encoding

The root object MUST be a MessagePack map with exactly these fields:

| Key | Type  | Meaning                                             |
| --- | ----- | --------------------------------------------------- |
| `l` | array | Directory entries.                                  |
| `t` | int   | Node type. MUST be `2`.                             |

The root `t` is the node type of the decoded object. This BUD defines node type `2` for directory manifests.

Each link is a map with these fields:

| Key | Type   | Required | Meaning                                                                 |
| --- | ------ | -------- | ----------------------------------------------------------------------- |
| `h` | bin    | yes      | 32 byte Blossom hash of the linked object.                              |
| `k` | bin    | no       | 32 byte client-side decryption key.                                     |
| `m` | map    | no       | JSON-compatible metadata for the link.                                  |
| `n` | string | yes      | Directory entry name.                                                   |
| `s` | int    | yes      | Plaintext file size, or total descendant file bytes for directories.    |
| `t` | int    | yes      | Link type: `0` for blob, `1` for file manifest, `2` for directory manifest, `3` for directory fanout. |

The link `t` is the type of the linked object. A link type equals the node type of the manifest it points at, except `t = 0`, which points at a raw Blossom blob that has no node type. Thus a `t = 2` link resolves to a `t = 2` directory node, a `t = 1` link resolves to a BUD-17 `t = 1` file-manifest node, and a `t = 3` link resolves to a BUD-17 `t = 3` directory-fanout node.

The `k` field MAY contain a client-side decryption key, such as a BUD-15 CHK key. Clients MUST treat `k` as a bearer secret and MUST NOT send it to Blossom servers.

For directory links where the total descendant file size is unknown, `s` SHOULD be `0`.

The `m` field MUST be a map with string keys and values from the metadata data model below. Clients MUST ignore unknown metadata keys when interpreting metadata, but MUST preserve them when reproducing the same manifest.

The `s` field MUST be an unsigned integer in the range `0` through `2^64 - 1`. Implementations MUST preserve integer values exactly or reject values they cannot represent; silently rounding them is not permitted.

The `n` field is required for links in a `t = 2` directory manifest because those links are user-visible directory entries. BUD-17 defines `t = 3` directory fanout nodes whose internal links omit `n`.

Link types `1` and `3` are defined by BUD-17.

Readers MUST return an unsupported type error for unknown link or node types. They MUST NOT reinterpret an unknown type as a blob or another known manifest type.

## Deterministic Encoding

To make manifest hashes reproducible:

1. The root map fields MUST be encoded in this order: `l`, `t`.
2. Link map fields MUST be encoded in this order, omitting absent optional fields: `h`, `k`, `m`, `n`, `s`, `t`.
3. Links in a directory manifest MUST be sorted by `n` using ascending bytewise order of the UTF-8 encoded names.
4. Metadata map keys MUST be encoded in ascending bytewise order of the UTF-8 encoded keys, recursively, including maps inside arrays. Keys MUST be unique within each map. Numeric-looking keys are strings: `"10"` sorts before `"2"`. Locale collation, UTF-16 code-unit order, and host-language object enumeration order MUST NOT determine the wire order.
5. Nonnegative integers MUST use positive fixint or the shortest unsigned integer format. Negative integers MUST use negative fixint or the shortest signed integer format. A signed encoding MUST NOT be used for a nonnegative integer.
6. Strings, binary values, arrays, and maps MUST use the shortest available length header for their type. Hashes and keys MUST use MessagePack binary types, not strings or arrays of integers.
7. Every string, including metadata keys and values, MUST be valid UTF-8. Encoders MUST reject unpaired Unicode surrogates instead of replacing them. Unicode normalization MUST NOT be applied: distinct code-point sequences remain distinct names and values.
8. Metadata array order MUST be preserved. Maps are unordered in the data model and ordered only for encoding.
9. Absent optional fields MUST be omitted, not encoded as `nil`. An absent `m` and a present empty `m` are distinct; encoders MUST preserve that distinction. Metadata values may themselves be `nil`.
10. The encoded blob MUST contain exactly one manifest, with no trailing bytes. Root and link maps MUST contain only the fields defined by this BUD; additional application metadata belongs in `m`.

### Metadata Data Model and Numbers

Metadata values are `nil`, booleans, valid UTF-8 strings, numbers, arrays of metadata values, and maps from valid UTF-8 strings to metadata values. MessagePack binary and extension types, including timestamp extensions, MUST NOT appear within metadata. Encoders MUST reject unsupported values rather than silently dropping or replacing them.

Integer inputs MUST be in the MessagePack range `-2^63` through `2^64 - 1`. Floating-point inputs MUST be finite IEEE 754 binary64 values. NaN and infinities are not allowed. A host's integer and floating-point representations of the same numeric value MUST produce the same bytes:

- An integral value within the MessagePack integer range MUST use the integer encoding above, even when supplied as a floating-point value. In particular, `1`, `1.0`, and `1e0` encode as `01`; positive and negative zero encode as `00`.
- Every other floating-point value MUST use float64 (`0xcb`), even if float32 could represent it exactly. For example, `1.5` encodes as `cb3ff8000000000000`.
- Exact integer values MUST NOT be rounded through a floating-point conversion. Hosts with limited integer precision need an exact integer representation or MUST reject unsupported integers. In JavaScript, this includes using `bigint` for integers beyond the safe `number` range.

### Reading Existing Manifests

These encoding requirements apply to newly written manifests. Readers MAY also accept older encodings with different field order, longer length or integer headers, or alternative numeric representations. A blob's hash MUST always be checked against its original stored bytes, never against a decoded and re-encoded representation.

Re-encoding a legacy manifest under these rules can change its hash and the hashes of ancestors that reference it. Existing references MUST continue to identify the original bytes; implementations MUST NOT silently replace those references with hashes of normalized manifests.

## Entry Names

Directory entry names:

1. MUST be valid UTF-8 strings.
2. MUST NOT be empty.
3. MUST NOT contain `/` or the NUL character.
4. MUST NOT be `.` or `..`.
5. MUST be unique within the same directory manifest.

Paths are resolved by splitting on `/` and matching each segment against a link `n`.

Clients MUST NOT percent-decode an entire path and then split on `/`. If percent-encoded paths are used in a higher-level URI or HTTP route, clients MUST split the path into segments first and decode each segment independently.

## URI Usage

Example:

```text
blossom:16121fa792b3afc72ec8bfc1dc85060518b6adba1429973ecc12891165cbe67e.bdir?xs=cdn.example.com
```

## Resolving a Directory

To resolve a path from a directory manifest, clients SHOULD:

1. Fetch the root manifest blob by its Blossom hash.
2. Decrypt it if the root reference has a key.
3. Decode it and verify `t = 2`.
4. Look up the next path segment by exact `n` match.
5. Resolve `t = 2` links as directories.
6. Resolve `t = 0` links as blobs.
7. Resolve `t = 1` links as BUD-17 file manifests, or return an unsupported type error.
8. Resolve `t = 3` links as BUD-17 directory fanout, or return an unsupported type error.

Clients MUST fetch linked objects by `h`. If `k` is present, clients MUST use it only locally.

## Security Considerations

A public directory manifest reveals entry names, sizes, metadata, linked blob hashes, and embedded `k` values. Clients that need to hide those values SHOULD encrypt the manifest.

Clients SHOULD bound manifest size, link count, recursion depth, metadata size, and total bytes fetched while resolving directories.

Clients MUST validate names and reject duplicate names before presenting or materializing a directory. This prevents ambiguous path resolution and unsafe filesystem writes.

### Recursive Metadata and Numeric Normalization

This vector uses one blob link with `h` equal to 32 bytes of `ab`, `n = "x"`, `s = 0`, and `t = 0`. Its metadata input deliberately uses noncanonical insertion order, integral floating-point values, negative zero, numeric-looking keys, and keys U+E000 and U+10000:

```json
{
  "values": [
    1.5,
    -0.0,
    4294967296
  ],
  "nested": {
    "\ud800\udc00": "astral",
    "\ue000": "bmp",
    "2": -0.0,
    "10": 1.0
  },
  "2": 2,
  "10": 10
}
```

The root has `t = 2`. In the nested map, U+E000 precedes U+10000 in UTF-8 byte order. The integral values become integers; `1.5` remains float64.
